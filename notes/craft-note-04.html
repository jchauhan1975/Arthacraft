Fix ten, lose one.

Growing a golden set without fooling yourself: acceptable instead of exact, the business holding the bar, and re-running everything on every change.

Jitander ChauhanNovember 20268 min read

Fix ten, lose one

We had a system that would not leave testing. Nothing failed loudly; things just kept quietly coming undone.

We would work through a list of issues, fixing the second, then the third, then the fourth, and by the time we had fixed ten, the first one had drifted. When we fixed it again, something else slipped, and we were going in circles.

Two things were wrong, and neither of them was the model. First, we were only re-checking what we had just changed, when any change can move answers that were already right. If the whole set is not re-run before every release, you will not see the drift until a user does.

Second, we were checking for the wrong thing. Our expected answers were exact answers, and the same input does not produce the same wording every time, even with randomness turned down to zero. [1] What got us out was asking a different question: instead of "does it match?", we asked "is it close enough to what we need, and do the facts behind it hold up?"

The wording could vary. The evidence could not.

In the terms of Part 1, this is consistency: the same input getting the same decision, release after release. Regression suites, held-back cases and the warning against tuning to a metric are all long-established practice. What follows is what applying them actually took, on a system that would not leave testing.

Acceptable, not exact

An LLM will not give you the same sentence twice. A golden set that stores exact answers will fail a good system forever, and a team chasing exact matches will keep re-tuning prompts that were never broken.

So each case has to describe what makes an answer acceptable, leaving the exact words open.

Facts that must be present

The figures, names, rules or conditions the answer cannot do without.

Facts that must not appear

The wrong policy, another client's terms, the invented number.

The evidence behind it

Where each fact comes from, so a check can confirm it rather than trust it.

What can vary

Wording, order, length and tone are all allowed to move.

Then decide how close is close enough. That is not an engineering decision. It is a business one, and it should be set per feature, according to what a wrong answer would cost. A draft summary can tolerate more variation than a coverage decision or a compliance check. In our case the bar was 90 percent, set with the business.

Treat the threshold as a setting that can change. Write it down, agree it with the business owner, and change it only on purpose.

The people who asked for it check it

The verdict on whether an answer is acceptable belongs to the same people who defined correct in the first place: the domain expert or business user who gave the requirement. They check it in two places.

In QA, before release

The business user runs real cases in a test environment and judges each answer against the agreed bar. What passes moves forward, and what does not goes back to the developers with the reason.

In production, after release

Users get a simple way to flag an answer that is wrong, incomplete or out of bounds, right where they see it, without a ticket system to learn or an email to write.

Both streams feed continuous improvement. The developers build the system and the business decides whether it works, and the golden set is where the two meet.

Growing in two directions, on purpose

A golden set grows in two directions.

New functionality

Every new capability needs its own approved cases before it ships, built the same way as the first set: real inputs, expert approval, out-of-bounds cases included.

New questions on existing topics

Users will ask what you already cover in ways you did not anticipate. The answers to those should land close to an already-approved answer, and they are checked against it rather than given a new definition of correct.

The set should not change every time someone comments, though, because what comes back from users is not all the same kind of thing.

A defect

An answer that fails the agreed bar: wrong facts, missing facts, an out-of-bounds question handled badly. It needs a fix, and a case that will catch it again.

Feedback

An answer that passes but could be better. "This is close, but if X were Y it would be more useful." That is valuable, but it is a change request rather than a failure.

Both go through the same process of being logged, reviewed and scheduled for a release, and nothing in the golden set changes on the spot. If expected answers shift every time someone has an opinion, the set stops measuring anything, and you are back to going in circles.

Re-run everything before every release

The cure for "fix ten, lose one" takes discipline more than cleverness: before anything is released, run the whole set. Regression testing matters more for LLM systems than for ordinary software, because a change in one place can move answers anywhere. Any of these means the next release runs the full set:

  1. A code changeHowever small.
  2. A model changeA new version, a new provider, or a provider update you did not ask for.
  3. A prompt changeWith one extra step, below.

Between releases, run what each change could affect, as often as you like. Running the full set on every small change sounds safe and quickly becomes the biggest cost you have; Part 6 shows how that happened to us, when agents re-ran the full test suite after every small commit. Part 8 sets out which checks run when.

Sometimes the prompt changes because the expected behaviour changed: a new format, a new rule, a different level of detail. Then the test cases have to change too, and this is the dangerous moment, because if you change the prompt and the tests together, a failing test can quietly become a passing one just because you edited it.

Change them deliberately instead. Say why the expected answer moved, get the business owner to approve it, and save it as a new version of the set. The old version stays, so you can see exactly what changed and why.

Don't tune to the test

There is a quiet way to fool yourself: adjust the prompt again and again until every case in the golden set passes. The trap is old enough to have a name: when a measure becomes a target, it ceases to be a good measure. [2] In model evaluation it shows up as scores that rise sharply once the test cases leak into what was tuned, and stop meaning anything. [3]

Two habits prevent it.

Treat the prompt as a contract for the output, not a dial for the answer. You can change the structure of what comes back (a table instead of a paragraph, new fields, a different order), but that must not change the reasoning. Only a change to the processing logic, the rules and evidence the answer is built on, should change the answer.

That gives you a test you can run on purpose. Ask the same question with different wording, or ask for a different output format, and check that the facts and the decision hold. Researchers call these invariance tests, and they find failures in systems that have already passed extensive testing. [4] If the facts move, the system is reacting to how the question was presented rather than reasoning about it.

Keep some cases back. Developers should not see every case they are graded on, so hold some back for the final check before release, and let the business users bring their own fresh questions in QA. Cases nobody tuned against are the only honest measure of whether the system works beyond the test.

A test you tuned against is no longer a test. It is a rehearsal.

Versioning and retiring cases

Treat a golden set as a controlled asset, the way you treat code, with every change versioned: what changed, why, and who approved it.

The set should shrink as well as grow. When a case no longer makes logical business sense, because a rule was retired, a product was withdrawn or a process changed, remove it. Keeping it means the system is tested against a business that no longer exists, and every failure on it is noise. Removal goes through the same approval as addition, and the old version stays on record.

How this changes by context

Enterprise

Versioned golden sets and recorded approvals are audit evidence, because they show what "working" meant on the day a release went out, and who agreed it.

Commercial

Each client's acceptance bar can differ. Keep their threshold and their cases with their own version history, so a change for one client never moves another.

Agentic

For agents, regression means checking the steps as well as the final answer. A format change that alters which tool the agent calls is the same defect as one that alters a fact.

What to do

  1. Store what makes an answer acceptable.Required facts, forbidden facts and evidence, not exact wording.
  2. Let the business set the threshold.Per feature, according to the cost of a wrong answer.
  3. Separate defects from feedback.Route both through a release process, not straight into the set.
  4. Re-run the whole set before every release.After any code, model or prompt change.
  5. Test that wording and format don't move the reasoning.Same question, different shape, same facts.
  6. Keep some cases back.For the final check, untouched by tuning.

What not to do

  1. Do not re-check only what you just changed.That is how the first fix drifts while you make the tenth.
  2. Do not change prompts and expected answers together without approval.That is how a failing test turns green.
  3. Do not let every comment change the set.A moving target measures nothing.

Growing on purpose

The questions will change.

The business will change its mind.

A golden set that grows on purpose, under the business's control, is how you keep up with both, and with the model underneath, without going in circles.
